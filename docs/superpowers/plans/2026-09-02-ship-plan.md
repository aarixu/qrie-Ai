# Ship plan — everything left, split by who does it

**Date:** 2026-09-02
**Source:** an external audit Aarav commissioned, spot-verified against this
repo on 2026-09-02. Five of its heaviest claims were checked by hand and all
five held: the two `VITE_` keys really are read in `ClassRoom.tsx:257-258` and
would be inlined into the bundle; `apps/agent/src/tokenServer.ts` really does
take `identity` straight from the request body with no verification; there is
no `supabase/` folder and no `.sql` anywhere; only `class10-blood` of fifteen
lessons has an `audio/` folder; and `class9-mathematics` has a full graph with
zero Maths lessons behind it. The audit is trustworthy — this plan is built on
it rather than beside it.

**How to read this.** Part A is work that needs nothing from Aarav. Part B is
work only he can do, written button by button. Part C needs one to finish
before the other can start. Inside each part the order is by DEPENDENCY, not
by severity — a thing that unblocks three others comes before a scarier thing
that blocks nothing.

## PART A — I do these, no interference needed

### A1. Stop the bleeding (this is the whole ship-blocker)

- [ ] **A1.1 Move the two live-tutor keys out of the browser.**
      `ClassRoom.tsx` reads `VITE_GEMINI_API_KEY` and `VITE_OPENROUTER_API_KEY`
      to build the doubt agent. Vite inlines every `VITE_` var into the bundle,
      so both are in `dist/assets/index-*.js` today. Route the doubt agent
      through `/api/llm` — which already exists, is tested, and holds no key in
      the browser — and delete both reads. The live VOICE agent needs a
      different answer (it opens a socket to Google directly); it moves behind
      a server-minted ephemeral token, or it comes out of the build until B2 is
      done.
- [ ] **A1.2 Write the Supabase Edge Function that hosts the relays.**
      `@ai-tutor/relay` is already pure and cloud-agnostic and its Node adapter
      already runs the dev server, so this is wiring: one function, five paths,
      the same `toRelayRequest`/`sendRelayResponse` pair. Deploying it is B3.
- [ ] **A1.3 Put a lock and a budget on every relay.**
      Verify the caller's Supabase access token; reject anonymous calls. Then
      per-user: a request-per-minute limit and a per-day token budget, both
      stored in Postgres so they survive a cold start. Without this, one leaked
      URL spends until the balance is gone — which nearly happened when the
      cloudflare tunnel was public.
- [ ] **A1.4 Authenticate the LiveKit token server.**
      `POST /token` must take an access token, verify it, and derive `identity`
      from the verified user id — never from the body. Same for `POST /doubt`,
      which dispatches a paid agent. Refuse a room the caller has no claim to.
- [ ] **A1.5 Commit the RLS migration.**
      The policy exists only as a docstring in `supabase.ts`. Create
      `supabase/migrations/`, put the table and policy in a real `.sql`, and
      write a test that a second user cannot read the first user's rows.
      Whether it is live on the project is B4.

### A2. Make it survivable on a real phone

- [ ] **A2.1 React error boundary at the root, and one per route.**
      A single render throw is a permanent white screen today. On a phone that
      is an uninstall. The boundary must offer a way back, not just an apology.
- [ ] **A2.2 Code-split the bundle.**
      One 1.56 MB chunk today, plus a 719 kB Draco decoder and a 285 kB WASM
      for `model3d`, which almost no lesson uses. Route-level lazy loading, and
      the 3D path loaded only when a lesson actually asks for it.
- [ ] **A2.3 Gate the dev labs out of production.**
      `/canvas-lab`, `/avatar-lab` and `/action-lab/:lessonId` are in the
      production router unguarded. A store reviewer can reach them.
- [ ] **A2.4 Stop the service worker swapping itself mid-class.**
      `sw.js` calls `skipWaiting()` and `clients.claim()`. A deploy during a
      class changes the app under the student. Hold the new worker and offer
      "a new version is ready" instead.
- [ ] **A2.5 Ask for the microphone warm, not cold.**
      One screen that says why before the browser prompt appears. Cold prompts
      are denied far more often on mobile, and an iOS denial is painful to
      recover from.

### A3. Kill the generic look (this is the "UI feels templated" fix)

- [ ] **A3.1 A real typeface pair, with Devanagari.**
      One system font stack is the single loudest templated signal. The content
      is Hinglish, so both faces must carry Devanagari or half the lesson falls
      back to a different font mid-sentence. Candidates: **Baloo 2** (Indian
      design, friendly, full Devanagari) as display, **Inter** or **Mukta** as
      body. Loaded self-hosted, subset, with `font-display: swap`.
- [ ] **A3.2 Replace Material Symbols.**
      The default Google icon set is the second loudest signal. **Lucide**
      (MIT, clean, tree-shakeable) behind the existing `Icon` component, so the
      swap is one file and every call site keeps working.
- [ ] **A3.3 Empty, error, offline and skeleton states.**
      Notes with no notes, Bookmarks with none, a class that failed to prepare,
      a dead connection, and a loading skeleton instead of a spinner. An empty
      screen is an invitation to act, not a blank.
- [ ] **A3.4 Screen transitions and button feel.**
      The CSS is written (`screen-enter`); it needs applying at the router.
      Reduced motion already neutralises it.
- [ ] **A3.5 Lesson-complete celebration.**
      The penguin cheers, the tick stamps on after him, the streak counts up.
      Half-built already; the patch anchor needs redoing.

> On "premium UI frameworks": the honest read is that this app already has a
> real token system, a dual theme and Duolingo-grade buttons — dropping in
> shadcn/ui wholesale would fight all three and cost a week for a sideways
> move. The generic feeling is **typography and icons**, which A3.1 and A3.2
> fix in a day. Borrow shadcn's *patterns* (focus rings, dialog behaviour)
> where ours are thin; do not import its design language.

### A4. Know what is happening

- [ ] **A4.1 Crash reporting** (Sentry free tier) — device, route, stack.
- [ ] **A4.2 Product analytics** (PostHog free tier) — which lesson they leave,
      which question everyone gets wrong, whether anyone finishes anything.
      Without this every product decision after launch is a guess.
- [ ] **A4.3 CI** — GitHub Actions running typecheck, tests and the production
      build on every push. 1,670 tests that only run on my machine are not a
      safety net for a repo whose stated purpose is handover.
- [ ] **A4.4 Release versioning** — build numbers that increase, a changelog,
      git tags. Both stores track updates by monotonic build number.

### A5. Product gaps I can close alone

- [ ] **A5.1 In-app account deletion, for real.**
      Settings has "Reset progress", which clears local state and leaves the
      Supabase user and their rows untouched. Apple has required real deletion
      since June 2022 and Google requires both in-app and a public web URL.
      This is an automatic rejection on both stores.
- [ ] **A5.2 Data export.** DPDP gives a right of access. One table today, so
      it is cheap now and irritating later.
- [ ] **A5.3 Content-safety layer on the live tutor.**
      An open-ended voice conversation with a child, with no moderation on
      either side, no log of flagged exchanges, and no way to report a bad
      answer. Store reviewers check this specifically in child-facing apps.
- [ ] **A5.4 Fix the Maths dead end.**
      306 nodes, zero lessons: a Class 9 student who picks Maths takes a
      placement test and gets a study plan where every step is a dead end.
      Either prepare Maths lessons or remove Maths from onboarding until they
      exist. Showing a dead end is worse than offering one subject honestly.
- [ ] **A5.5 Record the fourteen silent lessons.**
      One of fifteen has an `audio/` folder. The rest synthesise on every play
      — paying and waiting each time — or fall back to the browser robot.
      `packages/voice/README.md` names this exact failure as the thing the
      product exists to remove.
- [ ] **A5.6 Warm entry.**
      Aarav's own design: the student is in the room in ten to fifteen seconds
      while the class prepares behind them, and the tutor makes real
      conversation — "kal jo padha wo kaisa laga", or on a first visit their
      school and favourite subject. The answers feed the profile and the
      outcome map, so the wait becomes work rather than a spinner. This is what
      removes the need to batch-prepare content at all.
- [ ] **A5.7 Offline downloads.**
      The plumbing exists (service worker, network-first JSON). What is missing
      is "download this lesson", an offline indicator, and a student being able
      to tell what will work on the bus.
- [ ] **A5.8 Split the lesson format into spine + live fill.**
      Decided 2026-08-29 and never built: the recording carries the spine, the
      live tutor fills the personal parts. Today the recording is the whole
      class. This must land BEFORE a content library is built, because changing
      the format afterwards is expensive.

### B7. Phone OTP — read this before spending anything

Phone OTP in India is not "plug in Twilio". Transactional SMS needs **TRAI DLT
registration**: the entity and every message template registered, using
business documents (GST or incorporation), and it takes days. Without it
messages are blocked, not merely expensive.

There is no free SMS tier that survives production. Twilio and MSG91 both give
trial credit — Twilio's trial only sends to numbers you have verified, which is
fine for testing and useless for students.

**Recommendation: skip phone OTP until there is a registered entity.** Google
(B6) plus email covers the audience, and both are free. Revisit when the
company exists.

### B8. Legal pages — the stores will not accept the app without them

Both are public URLs, and both are needed before the Data Safety form or the
Privacy Labels can even be filled in.

1. **Privacy policy** — what is collected (name, class, email, answers, voice
   recordings), why, who processes it (Supabase, OpenRouter, Deepgram), how
   long it is kept, how to delete it, and a contact address.
2. **Terms of service** — including the accuracy disclaimer for AI answers.
   This is a board-exam subject; that sentence matters.
3. **A support inbox.** The Help screen has no destination today. Both stores
   require a working support URL and a contact address.

Generators get you 80% there (termly, iubenda). The AI-answers disclaimer and
the children's-data section need a human — ideally a lawyer, given B9.

### B9. Children's data — a decision, not a task

Class 6–12 is roughly 11 to 18. India's **DPDP Act 2023** requires verifiable
parental consent for under-18s. The codebase has no consent flow, no age gate
and no parent record, and onboarding asks for the class — an age signal —
before asking anything about consent. A single US signup adds COPPA.

I can build the age gate and the consent flow. What I cannot do is decide what
"verifiable" means for your product, or accept the liability. **Talk to a
lawyer before students are onboarded.** Realistic options: a parent email
confirmation step, or restricting signup to 18+ with a school/parent-managed
route for younger students.

### B10. Store accounts and listing assets

1. **Google Play Console** — one-time $25 → **play.google.com/console** →
   pay → identity verification (a few days)
2. **Apple Developer Program** — $99/year → **developer.apple.com/programs**
   → enrol → verification
3. Assets I cannot invent for you: app name, short description (80 chars),
   full description, category, IARC content-rating questionnaire, and the
   feature graphic 1024×500. Screenshots I can generate once the Capacitor
   build runs.

### B11. Payments — a decision first

Both stores mandate their own billing for digital subscriptions and name
education subscriptions explicitly. India allows Google's alternative billing
at a 4% lower fee. Before any of it is built, you decide: what is free, what is
paid, and at what price. Nothing can be implemented until that exists.
